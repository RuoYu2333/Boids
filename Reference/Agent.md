## 2. 最高优先级约束

### 2.1 原始 ZSF 工程不可访问

新的 Agent 看不到 `C:\zsf`。现有 Markdown 文档是唯一可用的项目事实来源。

文档中的 `C:\zsf\...` 路径是前一次分析时记录的历史源码定位信息：

- 可以用来解释某个结论原本来自哪个模块。
- 不代表新 Agent 能打开该文件。
- 不得声称已经重新检查这些路径。
- 不得因为无法打开路径而否定已记录的文档结论。
- 也不得根据文件名自行补全未记录的实现。

如果用户询问文档没有覆盖的源码细节，应回答：

```text
当前交接环境只有技术文档，没有原始 zsf 工程，因此无法进一步确认该方法或字段的实际实现。
如果提供相关源码片段，可以在现有文档模型基础上继续分析。
```

禁止：

- 假设本地存在 `C:\zsf`。
- 要求使用 `rg`、Unity、Git、SVN 或生成器重新扫描原工程。
- 声称某条结论已经在当前会话中由源码重新验证。
- 根据常见 MMORPG 经验杜撰当前项目的服务端或 Lua 细节。

如果需要新增文档，只能写入：

```text

```

```text

```

`E:\wmsj\documents` 是原有目录，不得无关覆盖。

### 2.2 不臆测服务端/Lua

原分析快照中的 `C:\zsf\Server` 主要是配置、地图和场景资料，不是完整服务端源码。

工作区仅有少量 Lua 示例/活动脚本，没有吃鸡、千里江山等副本的完整服务器 Lua 逻辑。


只能把第 1 层称为“原分析记录的客户端实现”。第 2 层应写成“服务端至少需要保证”或“协议推导”。第 3 层必须明确标记未知。

### 2.3 文档用于技术理解，不追求源码级复刻

## 4. 当前工程认知

原分析中的 `C:\zsf` 是一套大型 Unity MMORPG 多工程工作区；新的 Agent 只通过文档了解其结构：

| 目录 | 技术定位 |
|---|---|
| `Client` | Unity 2022.3.58f1 客户端，主要游戏 UI 使用 NGUI |
| `Public` | 配表、Proto、GameConfig、生成器和工具的事实源 |
| `Server` | 当前主要包含配置、地图和场景资料 |
| `Robot` | Unity 自动化/压测机器人，使用 FSM、AI 和独立网络栈 |
| `GMTool` | .NET Framework 4.7.2 WPF 运营管理客户端 |

核心跨端关系：

```text
Public tables / PBMessage.proto / GameConfig.ini
        |
        | 代码生成与同步
        v
Client / Robot / GMTool / Server consumers
```

不要把生成的 `Table_*.cs`、`PBMessage*.cs` 或 `ProtoPackets.cs` 当作事实源。

## 7. 四个具体功能的最小恢复摘要

### 7.1 王婆说媒

```text
4×9 Board
 -> 生成候选人
 -> 同类型同星级二合一
 -> 满足普通嘉宾需求
 -> 牵手得分
 -> 特殊嘉宾产生复合需求
 -> 需求占格并锁格
 -> 合成积累能量
 -> 王婆技能清除需求
 -> 暂停/结束/恢复
```

协议：

```text
CG_WANGPOSHUOMEI_OP  MessageID 3199
GC_WANGPOSHUOMEI_OP  MessageID 3200
```

关键技术点：

- 当前只对拖拽合成和能量增长做本地预测；牵手和王婆技能已改成收到 `UpdateGuest/UpdateCrazyGuest` 后权威落地。
- 推荐 sessionId + revision + expectedRevision。
- 每秒 SyncInfo 的时间权威和 QPS。
- 2026-07-29 快照已移除早期模拟嘉宾路径并修正胜利阈值；仍有 TODO、占位数据、弱类型参数和 `PlayCount` 缺少可见协议来源。
- 新增 `WangPoCrazyGuestFactor` 三档倍率/时间表，但客户端没有可见消费点，具体服务端算法未知。

### 7.2 吃鸡

协议：

```text
CG_OP_CHIJI_REQ  MessageID 2838
GC_OP_CHIJI_RET  MessageID 2839
```

`OpType` 约 49 类，覆盖：

- 职业。
- 航线和跳伞。
- 毒圈。
- 掉落实体和拾取。
- 技能。
- 击杀、结算和历史。
- 地图标点。
- 重连。
- 赛事与观战。

关键技术点：

- 毒圈只下发两个圆和三个服务器时间点，客户端按服务器时间插值。
- 掉落实体使用完整快照覆盖。
- 多人拾取原子性必须在服务端/Lua。
- 一个大消息复用大量 optional 字段和 parallel arrays，客户端必须按 OpType 严格校验。

### 7.3 千里江山 2D

协议：

```text
CG 2673
GC ENTER/STATE/SKILL/BOSS/SYNC_POS/RESULT 2674～2679
```

关键技术点：

- Controller 未加载时缓存 ENTER，STATE 保留最新快照。
- 主角资源加载完成发送 `LoadFinish(6)`。
- 玩家位置约 10Hz 同步。
- 服务端下发 Boss SkillID，客户端从 `Skill2D/Bullet2D` 重建弹幕。
- 弹幕包含追踪、弹射、定时、伸展和大风车状态机。
- 客户端碰撞后会上报 damage/HP；是否被服务端重新验证当前不可见。

### 7.4 天选锦鲤

协议：

```text
CG_LUCKYDRAW_OP 2814
GC_LUCKYDRAW_OP 2815
```

关键技术点：

- 多轮七状态时间机。
- 六位号码压为 int。
- 先按位置匹配，再做不考虑位置的多重集合匹配。
- 动画支持按开奖 elapsed 中途恢复。
- 领奖状态必须服务端幂等。
- 当前存在数字时间直接加秒、`TimeSpan.Seconds` 误作总秒数、跨分钟数字时间直接相减等风险。

### 7.5 帮战赛事服

协议：

```text
CG_GUILD_WAR_SAISHI_OP  MessageID 3203
GC_GUILD_WAR_SAISHI_OP  MessageID 3204
```

关键技术点：

- 新协议只管理赛季、四组 32 强 bracket、赛果和主播状态；战中复用原 `GC_GUILDWAR2_*` 战况包。
- 单场业务键是 `group + round + matchIndex`，生产实现还应加入 `season + revision`。
- `ReqBracket` 全量 replace，`NotifyStatus` scalar patch/可选 replace，`NotifyResult` keyed upsert。
- 季军赛使用 `round=3`，展示和赛程均映射到冠亚阶段 `stage=2`。
- 主播既有赛事层 `IsAudience`，也有角色创建层 `IsPvPAudience`；对象层隐藏自身并禁止隐藏其他参赛玩家。
- `GC_RET_GUILDWAR2_RESULT` 在“特殊服务器 + 帮战场景”双门禁下分流，避免污染原帮战结果链。
- 当前开关、服务器 ID 和三张赛事业务表均未形成可运行配置，完整服务端/Lua 逻辑不可见。

## 11. 常见错误

### 错误一：把客户端表现当服务端规则

Boss 播放技能、客户端产生弹幕，不代表 Boss 选技能的算法在客户端。

### 错误二：把客户端前置检查当安全校验

按钮不可点、玩家死亡不发包，只能减少无效请求；服务端仍要鉴权和校验。

### 错误三：忽略生成物边界

`PBMessage*.cs`、`ProtoPackets.cs` 和 `Table_*.cs` 是生成物。
